# Завдання: Нормалізація текстів Upwork Jobs

## 1. Мета

Перетворити різні за стилем, структурою та довжиною описи Upwork-джобів на стандартизовані описи фактичних задач для подальшого семантичного аналізу, генерації embeddings та кластеризації.

**Головний принцип:** виділити з вакансії те, що клієнт фактично хоче реалізувати, прибрати інформаційний шум і зберегти всі суттєві функціональні деталі.

Нормалізація повинна мінімізувати вплив довжини, стилю та структури оригінального опису на семантичну схожість вакансій.

## 2. Вхідні дані

Для кожної джоби:

- `job_id` — унікальний ідентифікатор.
- `title` — оригінальний заголовок вакансії.
- `description` — повний оригінальний опис вакансії.

Використовувати виключно інформацію з `title` та `description`.

**Не використовувати існуючі таксономії, категорії, skills або результати попередньої AI-класифікації.** Нормалізація повинна бути незалежною від попередніх інтерпретацій.

## 3. Вимоги до AI-обробки

### 3.1. Витягування оригінального опису задачі

Виділити з оригінального тексту фрагменти, які безпосередньо описують, що клієнт хоче розробити, налаштувати, інтегрувати, автоматизувати або змінити.

Вимоги:

- Зберігати оригінальні формулювання клієнта.
- Не перефразовувати та не змінювати витягнутий текст.
- Зберігати важливі технічні та функціональні подробиці.
- Якщо функціональні вимоги розміщені в різних частинах опису, зберігати відповідні фрагменти в початковому порядку, явно позначаючи пропущені частини.
- Не включати інформацію, яка не визначає функціональність майбутнього рішення.

Результат записувати в `original_text`.

### 3.2. Видалення інформаційного шуму

Виключити інформацію, яка не описує безпосередньо необхідну реалізацію:

- Загальні відомості про компанію.
- Вимоги до досвіду, кваліфікації та особистих якостей фрілансера.
- Вимоги до комунікації.
- Умови співпраці, оплати та графіка.
- Загальні рекламні й організаційні формулювання.
- Іншу інформацію, що не визначає функціональність рішення.

При цьому не видаляти технічні обмеження, особливості реалізації та конкретні вимоги до функціональності, навіть якщо вони згадуються серед вимог до кандидата.

### 3.3. Нормалізація тексту

На основі витягнутої інформації сформувати стислий, стандартизований опис необхідної реалізації англійською мовою.

Вимоги:

- Використовувати чіткі, нейтральні та однозначні формулювання.
- Описувати конкретно те, що потрібно реалізувати.
- Зберігати всі суттєві функціональні вимоги.
- Зберігати назви технологій, платформ, сервісів, API та інтеграцій.
- Зберігати логіку взаємодії компонентів, якщо вона зазначена.
- Зберігати інформацію про вхідні дані, обробку та очікувані результати, якщо вона присутня в описі.
- Не узагальнювати конкретну функціональність до надто широких понять.
- Не додавати технології, операції, архітектурні рішення чи функції, яких клієнт не зазначив.
- Не деталізувати реалізацію на основі власних припущень.
- Не додавати пояснень, оцінок або рекомендацій.

Функціонально однакові задачі, описані різними словами або з різною деталізацією, повинні отримувати максимально близькі за змістом нормалізовані описи.

При цьому нормалізація не повинна штучно робити різні задачі однаковими.

Результат записувати в `normalized_text`.

### 3.4. Витягування технологій

Сформувати масив `technologies`, який містить технології, платформи, сервіси та інструменти, явно зазначені клієнтом як частина необхідного рішення.

Правила:

- Зберігати конкретні назви технологій.
- Не додавати технології на основі припущень.
- Не замінювати конкретні технології загальними категоріями.
- Не включати технології, згадані виключно як загальні навички кандидата, якщо вони не належать до необхідного рішення.
- Уникати дублювання однакових технологій.
- Якщо технології не зазначені, повертати порожній масив.

### 3.5. Обробка комплексних джобів

**Одна джоба = один нормалізований опис.**

Не розділяти вакансію на окремі задачі.

Якщо клієнт замовляє декілька незалежних або взаємопов'язаних рішень, усі вони повинні бути представлені в одному `normalized_text`.

Не пропускати другорядні задачі лише тому, що вони відрізняються від основної.

Не вигадувати зв'язки між незалежними задачами.

### 3.6. Загальні правила

- Аналізувати кожну джобу незалежно.
- Не переносити інформацію між вакансіями.
- Не використовувати зовнішні знання для доповнення вимог.
- Не вигадувати відсутню функціональність.
- Не визначати або не додавати бізнес-ціль окремо.
- Не створювати окремі списки операцій, вхідних або вихідних даних.
- Зберігати оригінальний `title` без змін.
- Якщо опис недостатньо конкретний, не вигадувати відсутні подробиці.
- Якщо неможливо визначити фактичну задачу, повертати порожні `original_text`, `normalized_text` та `technologies`.
- Кожна деталь нормалізованого опису повинна бути підтверджена оригінальним текстом.

## 4. Очікуваний результат

Для кожної джоби сформувати один JSON-об'єкт.

```json
{
  "job_id": "12345",
  "original_title": "Telegram AI Bot Developer",
  "original_text": "Build a Telegram bot that receives customer messages, checks information against Airtable, uses AI to classify incoming requests, and saves the results in PostgreSQL.",
  "normalized_text": "Develop a Telegram bot that receives customer messages, retrieves information from Airtable, classifies incoming requests using AI, and stores processing results in PostgreSQL.",
  "technologies": [
    "Telegram",
    "Airtable",
    "AI",
    "PostgreSQL"
  ]
}
```

Вимоги до результату:

- Один результат на кожну вхідну джобу.
- `job_id` зберігати без змін.
- `original_title` зберігати без змін.
- `original_text` повинен містити дослівно витягнуту інформацію.
- `normalized_text` повинен містити стандартизований опис фактичної реалізації.
- `technologies` повинен містити лише технології, підтверджені оригінальним текстом.
- Результат повинен відповідати визначеній JSON-структурі.

## 5. Критерії якості

1. **Повнота:** усі суттєві функціональні вимоги збережені.
2. **Точність:** нормалізований опис не спотворює початкову задачу.
3. **Відсутність галюцинацій:** жодних вигаданих технологій, операцій або вимог.
4. **Семантична узгодженість:** однакові за функціональністю задачі отримують близькі описи незалежно від стилю та довжини оригіналу.
5. **Збереження відмінностей:** різні за функціональністю задачі не стають однаковими через надмірне узагальнення.
6. **Мінімізація шуму:** нерелевантна інформація не впливає на нормалізований текст.
7. **Перевірюваність:** усі факти нормалізованого опису можна підтвердити оригінальним текстом.
8. **Збереження комплексності:** усі функціональні задачі вакансії представлені в одному описі без втрати важливих деталей.
9. **Незалежність:** результати не залежать від існуючих таксономій та попередньої класифікації.

**Кінцевий результат:** для кожної Upwork-джоби отримати один максимально точний, очищений і стандартизований опис фактичної функціональності, який мінімізує інформаційний шум та зберігає всі важливі відмінності між вакансіями.
